# DECISIONS.md

Judgment calls made while building SiteVantage against the original spec, and
why. Read this alongside the code — comments in the source point back here
for the load-bearing ones.

## 0. Biggest deviation: this was built with no Xcode available at all

This session runs in a **Linux** container. There is no `xcodebuild`, no
Swift toolchain, and no iOS Simulator anywhere in this environment — Xcode
and the iOS SDK only run on macOS. That was discovered before writing any
code and flagged to the requester up front; they chose to proceed with the
full source written out unverified rather than pausing for a macOS build
target.

Practical effect on how this was built:

- The spec's build order says to build-and-verify-in-the-simulator after
  each of the 8 phases. That was impossible here. Instead, each phase was
  written to its real, final implementation in one pass (no shell-then-
  flesh-out double work), phase by phase, in the order the spec lists them.
- Verification was static only: every Swift file's braces/parens were
  checked for balance, every top-level type name was checked for
  collisions across files, and every call site was manually cross-checked
  against its target view's initializer signature. A generated
  `project.pbxproj` was validated by parsing every object ID reference in
  it and confirming there are no dangling or duplicate object IDs (see
  `scripts/generate_pbxproj.py` and the checks run while building this).
- **None of this is a substitute for an actual `xcodebuild build` /
  Simulator run.** The acceptance checklist's first item — "App builds and
  runs via `xcodebuild` in the simulator with no errors" — has **not**
  been verified and cannot be, from this environment. Whoever picks this
  up on a Mac should run:
  ```
  xcodebuild build -scheme SiteVantage -destination 'platform=iOS Simulator,name=iPhone 15'
  ```
  as the very first step, before trusting anything else in this list.
- **Update:** a GitHub Actions workflow (`.github/workflows/ci.yml`) now
  runs `xcodebuild build` and `xcodebuild test` on a `macos-14` runner
  (Xcode 15.4 pinned) on every push and PR. This is the first actual
  compiler this project has ever seen — check the Actions tab / the
  README badge before trusting a "no errors" claim from anywhere else in
  this document. If it's red, that supersedes every static-analysis claim
  made elsewhere in this file.

## 1. Project identity

- Org identifier: `com.sitevantage`, bundle ID `com.sitevantage.SiteVantage`.
  Not specified in the prompt; picked something bundle-safe and unique
  enough not to collide with a real org.
- `project.pbxproj` was **generated by a script**
  (`scripts/generate_pbxproj.py`), not created by hand or by Xcode itself
  (Xcode isn't available here). A ~40-file Xcode project has hundreds of
  cross-referencing object IDs; a generator is far less error-prone than
  typing them, and it's re-runnable if files are added later — just run it
  again after adding new files under `SiteVantage/`. Classic
  `PBXGroup`/`PBXFileReference` structure, `objectVersion = 56` (Xcode
  14/15-era format; newer Xcode opens/builds older-format projects fine).
  `CODE_SIGNING_ALLOWED`/`CODE_SIGNING_REQUIRED` are set to `NO` on the
  target so a Simulator build doesn't need a developer team configured.
- App icon and accent color are placeholder assets generated
  programmatically (`scripts/generate_placeholder_floorplan.py` and an
  inline icon-generation snippet), not designed brand assets.

## 2. Data model gaps filled in

- **`TicketMaterialItem` was added.** The spec lists `laborItems` and
  `equipmentItems` as ticket collections and separately lists
  `materialSubtotal` as a ticket field, but never defines a backing
  collection or line-item type for materials, even though `ProjectRate`
  already supports a `MATERIAL` item type. Added `TicketMaterialItem`
  (description, quantity, linked rate, calculated cost) for consistency —
  otherwise `materialSubtotal` would be permanently `$0` with no way to
  ever populate it.
- **`TicketEvidencePhoto.localFileURL` (spec) → `localFilePath: String`
  (implementation),** resolved against the current Documents directory at
  read time via `resolvedFileURL`. An absolute `Documents/...` URL is not
  guaranteed stable across app relaunches/OS upgrades/reinstalls (the
  container path can change), so persisting a relative path and resolving
  it live is the safer choice for something meant to be tamper-evident
  and long-lived.
- **`ProjectNoticeConfig` is a separate `@Model` class** (cascade-deleted
  with its `Project`) rather than an embedded struct, matching the "future
  sync layer" guidance in the prompt — a distinct model is easier to sync
  or version independently later than a struct baked into `Project`.

## 3. Screens / flows where the spec left the "how"

- **Jurisdiction e-sign disclosure:** only `"US"` ships with real
  ESIGN-Act-style consent copy (`ESignDisclosure.swift`). Every other
  jurisdiction choice (`CA`, `UK`, `OTHER`) gets a generic placeholder
  disclosure with an explicit caption to have counsel confirm local
  requirements — writing real jurisdiction-specific e-signature legal copy
  for multiple countries is out of scope for an engineering judgment call.
- **Manual pin doesn't store a real geo-position.** There's no model field
  for "pin position on the placeholder floor plan," and the floor plan
  itself is a synthetic generic grid with no real-world coordinate
  mapping (no per-project floor plans exist yet, per spec §4). So
  `ManualPinView` exists to force an explicit foreman gesture/acknowledgment
  before falling through to `locationSource = .manualPin` /
  `locationConfidence = .declared` with `nil` coordinates — it is a
  deliberate-action gate, not a geo-referencing tool.
- **Ticket-level location fields** (`FieldTicket.locationSource` /
  `.geoLatitude` / etc., as distinct from each photo's own location) are
  seeded from the **first** evidence photo captured on that ticket. The
  spec has both a ticket-level location and per-photo locations but never
  says how they relate; "first photo sets the ticket's location, same as
  the photos' own is the more precise source of truth" was the simplest
  consistent rule.
- **Materials are managed on the Pricing step, not Scope Review.** Spec §4
  screen 3 talks about labor/equipment parsing from voice; materials are
  never voice-parsed and don't fit that flow, so material line items
  (add/edit against the `MATERIAL` rate sheet) live on the Pricing step
  instead, alongside the rest of the cost breakdown.
- **Rate Sheet "delete" archives, not hard-deletes** (`ProjectRate.isArchived`).
  A rate already linked to a signed, historical ticket must not silently
  vanish and break that ticket's pricing/audit trail — archiving keeps it
  out of new-ticket pickers while leaving old tickets' linked rates intact.
- **App-level Settings screen** (current user name/title, high-contrast
  toggle, single-device disclaimer) is reached via a gear icon in the
  Projects & Rates tab's toolbar, not a third tab — the spec is explicit
  the `TabView` has exactly two tabs (Tickets, Projects/Rates) but also
  requires a Settings screen with specific content; a toolbar entry point
  satisfies both.
- **"Active project" concept:** the spec says the Ticket List shows
  tickets "for the active project" but never defines how a foreman picks
  which project is active. Added `AppSettings.activeProjectID` plus a
  project-switcher (toolbar button when >1 project exists, or a swipe
  action in the Projects list) to make that concrete.

## 4. Implementation choices within spec-approved options

- **Camera capture uses `UIImagePickerController` with
  `sourceType = .camera`,** which the spec explicitly allows as an
  alternative to a raw `AVCaptureSession` pipeline. Chosen for reliability
  and far less code while still fully satisfying "camera only, no gallery,
  no `PHPickerViewController`" — the picker is configured so there is no
  UI path to an existing photo.
- **Signature capture uses a SwiftUI `Canvas` + `ImageRenderer`,** not
  PencilKit — the spec allows either. No PencilKit-specific tools
  (markup, ink types, Apple Pencil pressure/tilt) are needed for a single
  flat signature stroke capture, so the simpler, dependency-free option
  was used.
- **Voice line-item parser (`FieldItemParser`) is intentionally simple:**
  keyword list + regex for "`<n> <trade word>`" and "`<n> hours`" patterns,
  per the spec's explicit "do not over-engineer an NLP pipeline"
  instruction. It is documented in-code and in the UI (a "SUGGESTED" badge)
  as non-authoritative — every parsed field remains directly editable, and
  editing a suggested field's description or headcount clears the
  "suggested" flag.
- **High-contrast mode is a lightweight, app-wide toggle:** forces dark
  color scheme, swaps the tint color, and every interactive control uses a
  shared 44×44pt `fieldTapTarget()` modifier throughout the app (not just
  when high-contrast is on — big touch targets are unconditional per spec
  §6). This is not a full per-screen re-theming system; it satisfies the
  "gloved hands / direct sunlight" accessibility requirement without
  building a full design-token theming layer for a v1 field-capture app.
- **Ticket serials are derived by scanning existing tickets on the
  project** (`TicketSerialGenerator`) rather than kept in a separate
  stored counter. This means serials never repeat for tickets that still
  exist and gaps from deleted tickets are fine and expected; the only
  edge case is that deleting the single highest-sequence ticket and then
  creating a new one will reuse that exact number — acceptable for a
  single-device, single-foreman build with no concurrent writers.

## 4b. Added a real XCTest target after the fact

The original build had zero automated verification — everything in §0 is
static analysis, not compilation. Added a `SiteVantageTests` unit test
target (also generated by `scripts/generate_pbxproj.py`, which now emits
both targets, their `PBXTargetDependency`/`PBXContainerItemProxy` wiring,
and a `TestAction` in the shared scheme) covering the pure-logic pieces
that don't need SwiftUI or the Simulator to exercise meaningfully:
`PricingCalculator`, `FieldItemParser`, `TicketSerialGenerator`, and
`NoticeDraftGenerator`. Tests use a real in-memory `ModelContainer`
(`isStoredInMemoryOnly: true`) rather than loose, unattached `@Model`
instances, per Apple's documented SwiftData testing pattern.

Writing these tests surfaced one real bug in `FieldItemParser`: the
equipment-keyword list contains `"mini excavator"` and `"excavator"` as
separate entries, and `"mini excavator"` contains `"excavator"` as a
substring — so a transcript mentioning "mini excavator" produced *two*
equipment suggestions instead of one. Fixed by matching longer keywords
first and skipping any shorter keyword whose match range overlaps one
already claimed.

## 5. Explicitly NOT built (per spec §7)

Confirmed nowhere in this codebase: any networking/API client code, a
PM/Commercial Desk web dashboard, live ERP/Sage/Viewpoint/Procore sync, BLE
beacon support, actual email/SMS/portal sending of anything, multi-user
auth/login, or a cloud transcription refinement pass. `voiceTranscriptionSource`
and `noticeConfig.autoSendApproved` exist as schema-only placeholders for a
future build, exactly as instructed — no code path ever exercises the
cloud/send side of either.
